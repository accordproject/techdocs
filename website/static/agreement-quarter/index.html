Accord Project · Agreement 1.0 · Draft proposal

Agreements that keep their word, wherever they run.

Accord Project is open-source software for agreements that are both legal text and running code. A template holds an agreement's text, the data it is drafted from, and logic that responds when something happens, such as a payment arriving or a deadline passing. Agreement 1.0 proposes how such agreements run, so that any system can host one and get the same result: the text a party signs is the text that runs, a clause does what its interface says, and the same request gives the same answer on any host.

DraftThis is a proposal for discussion, not a released specification. Nothing on this page is built into a release yet, and names, shapes and details may change before 1.0.

How to read the walk

An agreement is a legal instrument, so the page lays the engine out as an Inn of Court, where lawyers keep their chambers. Each room stands for one part of the design, as the table below lists, and each stop's heading names its room and its plain topic. The characters stand for the parts that act.

Counsel
The template author, who drafts the terms and their logic.
The lantern-headed clerk
The engine, a small automaton. It does the same work the same way every time, and it never leaves the court: no clock, no storage, no network, no keys. It carries each request to the template's window that serves it.
The registrar
Accord Project, which publishes the models.
The porter
The host. It keeps the keys, the clock and the records, and passes work through the lodge window.
A petitioner
A caller: a person or a system making a request.

The design in brief

At the centre is one call. The host, the system that stores an agreement and connects it to the outside world, passes in the agreement, its state, a request and what it has verified. The engine returns one of three results. Two other engine operations sit beside the call: instantiation, which checks a new agreement and commits its first state, and drafting, which turns a template and its data into text and its hash. Nothing else crosses the boundary. In the current release the engine reads the machine's clock, takes the caller's word for who is calling, and leaves its duties to the host unstated. In 1.0 the call is pure: the same inputs always give the same answer, so any host can run it, a request can be retried safely, and one engine can be checked against another.

Existing templates keep working. The current API stays beside the new one, deprecated but not removed at 1.0, and a compatibility adapter runs an existing template unchanged, keeping today's behaviour: the machine's clock and no identity. The Roll, at the end of this page, lists every change from the current release.

Around that call, an agreement holds one or more documents, such as a licence and its schedule, and each document can be built from reusable clauses. Each clause is its own template, plugged into a named slot through an interface it declares, and the engine checks the fit when the agreement is made. Data another system keeps, such as a sales total, arrives as typed facts the host supplies with each request. Authority comes from the callers the host has verified (principals), never from the template or the request. Text is identified by its hash, so a signature binds the exact words a signer saw. Shared test vectors define correct behaviour, so a second engine can prove it conforms.

Accord Project specifies only what crosses the engine's boundary. Persistence, scheduling, delivery and integrations belong to the host, which may be a mock, a serverless function or a commercial server. The operator is the business that runs the host, and it owns the calendar: business dates, cut-offs and month-end. Signed authority (approvals, delegated consents, attestations and evidence) is left to extension packages that domain communities own.

The running example is an agreement of two documents: a copyright licence, with an inline payment clause and a composed late payment clause, and the licensed-work schedule beside it. Many agreements are made from one template; the stops below follow one of them. The whole example is worked through as files you can read and run on the copyright licence sample branch of cicero-template-library: the licence, its schedule and late payment clause, the agreement record (agreement.json) and recorded test vectors. Like this page, it is a draft.

No. 1 · The Registry · Models 1.0

Plain data in the register, in volumes that never change.

The Registry holds the models: type definitions written in Concerto, Accord Project's schema language. A namespace is a versioned package of types, and a concept, a transaction and an event are kinds of type. A published version is never rewritten. A template's model declares one concrete TemplateData subtype and, if the template has logic, one StateData subtype. The base namespaces also hold the types that cross the engine's boundary: the inputs and the facts they carry, principals, the three results, what logic emits, outcomes, timers, artifacts, and the decorators that describe an interface member. They replace the current org.accordproject.runtime@0.2.0 types: State becomes StateData, and Request and Response keep their names.

Shape
concept CopyrightLicenseData extends TemplateData { … }
// Every template with logic has a state type:
concept CopyrightLicenseState extends StateData { … }
// runtime@1.0.0: Inputs, SystemPrincipal, ActorPrincipal,
//   Assurance, Committed, Rejection, Fault, Declined, Emitted,
//   Notification, Effect, Obligation, EffectOutcome, Timer,
//   Artifact, OperatorRequest,
//   and the decorators Returns, Declines, Emits
// Composition is declared in the template's manifest,
// not in its models.
TemplateData
The root is the one concrete concept that extends TemplateData, so the @template decorator and the Contract or Clause supertype go. This TemplateData is a Concerto concept; in the current release the same name is a TypeScript alias for IContract | IClause.
StateData
A template with logic keeps state, even if it has nothing to keep: it then extends StateData with no fields. A text template has no logic and no state, so it needs no StateData.
Decorators
@Returns, @Declines and @Emits are declared in the runtime namespace, each as a concept extending concerto.decorator@1.0.0.Decorator. The engine loads models with Concerto's check for undeclared decorators turned on, so a misspelt one fails to load.
PartyRef
A portable reference to a party.
PreciseAmount
An integer unscaledValue, held as a string of digits, plus a scale, with exact arithmetic. It is a string because Concerto's Long loses precision above 2^53. This is the money@1.PreciseAmount the current release already drafts.
Requests
Requests and responses are Concerto transactions, including EffectOutcome and every Declined. What logic emits is a Concerto event.
@1.0.0
A published version never changes. A CI check enforces it, so a model can't change under a stored agreement.

Template authors change

  • Remove @template and the Contract or Clause supertype.
  • If the template has logic, add a StateData subtype, empty if it keeps nothing.
  • Use PreciseAmount for money and PartyRef for parties.

What you get

  • Exact money, and types that never change under you.
  • One model for what a host sends and receives, in any language Concerto generates.

No. 2 · The Conveyancer's · Documents and clauses

Every deed in one bundle, each with its clauses bound in.

At the Conveyancer's, the deeds of one agreement are tied into one bundle, and each deed has its clauses bound in. An agreement is a container of documents, as in models#200. Each document is the root of its own tree, and each clause composed into it fills a slot that the document's manifest declares. One document is primary, and a caller's request enters there. A single template is an agreement of one document.

Shape
Agreement { agreementId, agreementHash, primary,
            documents, parties: PartyRef[] }
AgreementDocument { documentId, documentHash,
                    template: contentHash, data,
                    clauses: map<slot, Clause>,
                    references: map<name, documentId> }
instance id = document id, then slot path:
  licence, licence/late-payment, schedule
template
Named by content hash, so a replay knows exactly which logic ran. A template ships as an archive: its text, models, logic and a package.json manifest. The engine checks every archive against its hash.
data
Canonical, complete and already merged. Where a value comes from is the host's concern; instantiation refuses incomplete or invalid data.
Primary
A caller's request enters the primary document's root, which needs logic. Outcomes and timers go straight to the instance that emitted or set them, in any document. The engine computes agreementHash and documentHash, and a supplied value must match.
References
A document reaches another only through a reference its manifest declares, by template hash or by interface, and the agreement says which document fills it. Logic reads that document's data through self.documents.<name> and, if it has logic, triggers it through its interface, as it would a clause. Each call is a savepoint. References are checked when the agreement is made and may not form a cycle.
Slot paths
Instance ids are a document id, then a slot path. A slot that holds several clauses keys each by a value from its data, never by position, so removing one moves no other.
No reaching up
A clause never reads its parent's data or state directly. What it needs from above arrives in one of two declared, typed ways, checked when the agreement is made: a binding, for a value that does not change, or a fact the nearest ancestor provides, for live state (see No. 5). Nothing is copied implicitly.
Text templates
A template with no logic is drafted, never triggered. It can be a document of its own, like the schedule, or fill a slot and be drafted in place, inside its parent's text. It has no state, no revision and no handlers.

Template authors change

  • Nothing for a single template.
  • A reusable clause becomes its own archive, implements an interface, and is composed into a slot.
  • A document that relies on another, as a licence relies on its schedule, declares it in its manifest's documents.

What you get

  • A clause written once and composed into any document that declares its interface.
  • A missing or mismatched clause found when the agreement is made, not at run time.
  • Each document drafted and signed as itself, inside one agreement.

No. 3 · The Strongroom · Agreement state

A pigeonhole for each instance, a new number for every commit.

The Strongroom files each instance's state in its own pigeonhole, and the agreement takes a new number on every commit. The agreement's state is one index from instance id to that instance's own state. The engine takes the agreement at revision N and returns N+1. Each instance with logic also keeps its own revision, which moves only when its state changes. A caller whose decision rests on what it read can name that revision.

Shape
AgreementState { agreement, revision,
                 states: map<instanceId, InstanceState>,
                 pendingEffects, timers }
InstanceState  { template, revision, state }
revision
The agreement's revision orders its commits. How a host serialises concurrent requests is the host's choice.
expect
Optional. A caller's inputs may name any instance in the tree and the revision it read: expect: {instance, revision}. If that instance has moved on, the result is a standard StaleRevision Rejection, and the host may retry against the new revision. A request without expect is never stale: the logic judges it against the state as it stands. Outcomes and timers never carry it.
Approvals
An approval signs one instance's terms version, not its revision. The terms version is digestOf({textHash, data}) for that instance, and its text includes any clause drafted in place. A change to the instance's own text or data, or to a clause drafted inside it, voids the approval; a change to a parent or a sibling does not. A party's acceptance of the whole agreement binds the agreement's terms version instead: the digest of every document's terms version, so a change to any document voids it. Re-pinning to a fixed template (see the example below) keeps both text and data, so approvals in progress survive it. An act with no id of its own, unlike an acceptance with its acceptanceId, binds the instance revision instead.
Revision 0
Making an agreement runs the init of each instance that has logic, in tree order, a parent before its clauses, and commits revision 0. A failing init creates nothing. A text template has no entry in the index.
Validated
Each entry names the template that wrote it, and its state is validated against that template's StateData on load and on commit.
Lineage
The engine keeps no history. A host that needs one records each commit, for example as a hash chain over the spec's one canonical JSON form.
pendingEffects
Effects still awaiting an outcome, so a duplicate EffectOutcome is discarded.

Template authors change

  • Nothing for upgrades in 1.0. To ship a fix, the host re-pins live agreements to the new template version's hash, which needs no code (see below).

What you get

  • A stored entry that says which template wrote it.
  • Approvals that stay valid through a re-pin, and while other parts of the agreement move.
  • An agreement whose signed text never changes silently.

Shipping a fix to a live licence

An agreement is pinned to its templates by content hash. In 1.0 the host may re-pin it to a new template version, but only when nothing the parties signed or stored changes shape.

  1. The same text. The new version drafts the same text hash from the same data.
  2. The same state. The stored state still validates against the new version's StateData.
  3. The same slots. Every slot path is unchanged, so no state key moves.
  4. A check and a swap. The host records the template hashes it replaced. Pending effects and timers carry across.
  5. Approvals survive. The terms version hashes the drafted text and data, not the template, so a logic-only fix leaves an acceptance in progress valid.

Later minor versions add, without breaking 1.0, upcasters that change the shape of data and state (.migrate(from, to, {state, data}), never the text), an upgrade sent as a system request, amendments that produce a new version of the data, and a chain of text versions.

No. 4 · The Clerks' Windows · Logic and inputs

The caller asserts. The host attests.

Each window is a handler in the template's logic, and serves one kind of request. Logic registers one handler per request type, and one per effect type it emits, for that effect's outcome. The request is what the caller claims. The inputs are what the host vouches for: who is calling and what it verified, the business time, the requestId, the facts the agreement's templates read, and optionally the instance and revision the caller's decision rests on. The host does all the cryptography; the agreement deals only in principals.

Shape
Inputs { principal: SystemPrincipal | ActorPrincipal,
         businessTime, requestId,
         facts,   // keyed by instance and read name
         expect? { instance, revision } }
ActorPrincipal { actor, onBehalfOf?, assurances }
  // e.g. PasskeyApproval { by, digest, profile }
defineLogic<Self>()
  .init((self, activate) => …)
  .on(RequestType, (request, self) => response)
  .onOutcome(EffectType, (outcome, self) => …)
self.principal
From the host. actor is who is calling (a person, a system or an AI agent) and onBehalfOf the party it claims to act for. A lint flags any request field named like an identity, a time or a key.
Assurances
Proofs the host checked for this request, such as a passkey approval of a given digest. Each names the trust profile it was checked under, with its version: a published rule set for that kind of proof, such as which algorithms count. The package that defines the assurance type publishes its profiles.
self.now
The business time, a UTC instant that never goes backwards. The time an event happened is request data. A business date, or any other calendar position the operator owns, is a host fact, never worked out from business time.
self.state
Deep-frozen. A handler changes it only by passing setState a whole new value, committed with the response and discarded on a Declined.
Nothing looked up
Everything a run reads is in the data, the request, the inputs or the state. Outside information arrives only as data checked at instantiation, a fact the host supplies in the inputs, a request, or an effect outcome. A check at decision time, such as screening the licensee, is an effect whose outcome the clause waits for. So a replay needs nothing beyond the requests and their inputs.
Concurrency
The host's, not the template's. Logic decides against the snapshot of facts in its inputs as if nothing else happens, and an effect carries no version or precondition. The host keeps the snapshot true: it holds the records it read until their effects are taken, or checks their versions before it commits and, if one moved, triggers the request again with fresh facts.
Synchronous
Handlers are synchronous, and so are the engine operations trigger and draft: every archive is already in memory. Handlers are keyed by the classes Concerto's TypeScript codegen emits, and coverage is checked at load time.

Template authors change

  • Take time and identity from self, never from the request.
  • Check that the right party approved the right digest, and leave signature checks to the host.

What you get

  • A caller can't backdate a request, impersonate the licensee, or supply the key its own signature is checked against.
  • No cryptography in template code, and algorithms that change without touching an agreement.

No. 5 · The Library · self, composition and facts

Read through the glass. Take down only what a clause declares.

In the Library, a template writes only in its own volume; facts and other clauses are read through the glass. self is the template's own instance. A parent reaches a composed clause only through an interface the clause declares, never its raw state, and learns what the clause decided from its response. What a clause needs from above arrives as a binding or a provided fact, and what a template needs from outside arrives as a fact the host supplies. So a clause can change inside without breaking its parent, and a missing clause is found when the agreement is made, not at run time.

Shape
// The interface: a namespace of members, each describing itself
namespace org.accordproject.latepayment.api@1.2.0
@Returns(ReminderSent)
@Declines(ReminderLimitReached, NothingOutstanding)
@Emits(LateFeeAccrued)
transaction PaymentOverdue extends Request { }
@Returns(LatePaymentCleared)
transaction PaymentSettled extends Request { }
transaction ReminderLimitReached extends Declined { … }
transaction NothingOutstanding extends Declined { }
// What is owed, the clause reads as a fact its parent provides

// The clause's package.json
"accordproject": {
  "implements": { "org.accordproject.latepayment.api": "1.2.0" }
}

// The licence's package.json
"accordproject": {
  "slots": {
    "latePayment": {
      "interface": "org.accordproject.latepayment.api@^1.0.0",
      "optional": true,
      "bind": { "utcOffset": "utcOffset" }
    }
  },
  "documents": {
    "schedule": { "template": { "hash": … } }
  },
  "reads": {
    "sales": {
      "interface": "org.accordproject.royalty.api@^1.0.0",
      "fact": "SalesToDate", "key": "salesAccountId"
    }
  }
}
Interfaces
Versioned Concerto namespaces with no marker type. Every non-abstract transaction that extends Request is a member. A published version never changes.
Members
Each describes itself with decorators the runtime namespace declares: @Returns lists what it answers with, @Declines what it may decline with (without it, the member never declines), and @Emits the notifications a template may emit while handling it. Concerto validates every argument, and the decorators survive into the metamodel JSON, so any engine or host reads them without running code. Listing several types needs variadic decorators in Concerto, tracked in concerto#1640.
Who they bind
Every instance that handles the request type, whether or not it implements the interface, so a caller can type the answers from the request type alone. The same decorators describe a root template's own requests.
Operator requests
A member that extends OperatorRequest is one the host sends on its own calendar, such as month end.
The manifest
A template lists the interfaces it implements, each at an exact version, its slots, each asking for an interface with a semver range or for one template by hash, the other documents it relies on, asked for the same way, and the facts it reads. The models stay plain data, and the template hash covers these four sections.
Slot kinds
Required, "optional": true, or "many": true with the path of the key in each clause's data. A clause may implement several interfaces, including two majors of one. A slot that names an interface needs a template with logic. A slot that asks for one template and names no interface can hold a text template, drafted in place.
Bindings
For values that do not change. A slot binds a top-level field of the clause's data to any path in the parent's. The engine resolves it when the agreement is made, checks the types, and stores the value in the clause's data, so the clause's text and hash show it. Agreement data may not set a bound field, and an optional source bound to a required field is refused at load. The licence binds its utcOffset into the late payment clause.
Facts
For values a system of record owns. A template lists them in reads, each with a fact interface's semver range and the path in its own data that names the record, and logic reads them from self.facts, typed by codegen. An optional fact is a typed undefined. Facts arrive in the inputs, not in caller requests, because a caller could assert them and a timer or outcome could not carry them. The licence reads SalesToDate from the sales registry to work out royalties, and keeps no copy.
Host facts
Before each request, outcomes and timers included, the host reads every declared fact once and passes it in the inputs, keyed by the reading instance and the read's name, with the version of the record it read. Every read in one request sees the same snapshot. The engine checks each fact is the record the key names. Logic never sees the version. A required fact missing when logic reads it is a Fault.
Provided facts
For a parent's live state. A parent lists a fact interface in implements and provides each fact with a pure function, .provide(Fact, self => …). A clause reads it through reads and self.facts, exactly as it reads a host fact. The nearest ancestor that implements the interface provides it; if none does, the host supplies it, so one clause works composed or alone. A provider gets a read-only self, and a provided fact is computed when read and never recorded. Facts inform; they never authorise.
Clause handle
data and trigger, with no state. A repeated slot is a map by key. A document handle, self.documents.<name>, is the same, with trigger only for a document with logic.
Codegen
Turns the slots and their interfaces into the template's Self type, and the decorators into types, so a handler that returns a type its member doesn't list fails to compile. Generated types are named by namespace and version, so one build can hold two versions of an interface.
Instantiation
A missing required clause, a clause that doesn't implement its slot's interface, or a binding whose types don't match fails when the agreement is made.
Dispatch
By request type, falling back to the nearest supertype. A slot that asks for ^1.0.0 accepts a clause that implements 1.2.0.
Coverage
The engine checks at load time that logic handles every member of every interface it implements, every effect type it emits, and every fact it provides.

The licence calls its late payment clause when the fee is overdue

// Optional: the compiler makes you handle its absence.
const latePayment = licence.clauses.latePayment;
if (latePayment) {
  const reply = latePayment.trigger(PaymentOverdue.create({}));
  if (ReminderLimitReached.is(reply)) {
    // The clause's writes are discarded. The licence may pass the
    // decline up unchanged, decline itself, or commit its own
    // changes without the clause's.
  }
}
// A required slot needs no check: instantiation guaranteed it.

No. 6 · The Chancery · Results

Sealed together, or not at all.

The Chancery seals a request's documents together under one press, or seals none of them. A request is all or nothing, and each clause call is a savepoint inside it. The engine returns one of three results, and only Committed changes anything. Without this, a late payment clause could be discharged by a payment the licence then refused.

ResultMeansThe host
CommittedThe response, new state, notifications, effects, timers set and cancelled, artifacts, and the revision from and toStores it, delivers the effects and notifications, sets the timers
RejectionA response that extends Declined, answering a caller's request or reporting StaleRevision, and declinedBy, the instance that declined; no state change, no effects, no revisionMay log it and cache it by requestId
FaultAn error, including a resource limitRetries, or raises it with an operator
Decline or fail
A template declines by returning a Declined subtype. An uncaught error is always a Fault.
Savepoints
When a clause declines, its subtree's writes, effects, timers and notifications are discarded and the parent gets the Declined back as a value. When the primary document's root declines, the request is a Rejection. A Fault anywhere faults the whole request.
Typed responses
A response, accepted or declined, must be assignable to a type its member's @Returns or @Declines lists; a template's own subtypes are allowed. An instance may also pass up, unchanged, a Declined a clause returned to it in the same request. Anything else is a Fault, at the root as at any clause.
declinedBy
The instance that made the decline, so a decline passed up unchanged says honestly which document refused. For the engine's own declines, it is the instance they concern: the expect instance for StaleRevision, the primary document's root for RequestNotAccepted.
Callers only
Only a caller's request is rejected. A decline from a timer firing or an operator's request comes back inside a Committed result, with the timer consumed; a decline from an outcome handler is a Fault.
Semantic body
What the vectors compare, byte for byte.
Provenance
The engine build, the semantics version and timings. Vectors exclude it, so two engines can agree.

No. 7 · The Seal Office · Factories, hashes and drafting

Every value sealed by its type, every text by its hash.

The Seal Office keeps a seal for every type and every text. Every value is made with its type's generated factory. A template is named by the hash of what runs and drafts, and drafting is an engine operation inside the deterministic surface, because a signature binds the exact text the signer saw. There are two layers: the runtime, which is portable, and drafting, which runs through the TypeScript reference drafter.

Shape
Accepted.create({ … }) · LicensedWorkSchedule.is(data)
// Files sorted by path:
templateHash = sha256(canonical([{ path, sha256 }, …]))
TemplateReference { hash, name?, version?, location? }
// Returned as an artifact:
self.draft(template?, data?) → { text, hash }
Factories
Generated by npm run compile; no hand-written $class.
Two layers
The runtime layer is trigger: logic, state, effects, timers and facts. It is language-neutral, so a template's compiled logic.ts could run on an engine written in another language, and a second engine must match it byte for byte. Drafting turns a grammar and data into text, through the reference drafter. It depends on TypeScript by design, so it is shared, not reimplemented: any engine calls the reference drafter, and text hashes compare across hosts.
The hash
Covers only what runs and drafts: the grammar, the models, the logic if it has any, the implements, slots, documents and reads sections of the manifest, the engine semantics version and the default utcOffset. A compiled archive's hash covers its JavaScript; a source archive's covers its TypeScript, and the compiler version is recorded. The README, samples and descriptive metadata sit outside it, and a name and version are labels that point at a hash, so fixing a README needs no re-pin.
References
A parent fixes a clause with a TemplateReference, and the parent's hash covers the clause's, like a lockfile. The hash is authoritative; the host resolves it from any store and the engine never fetches.
self.draft
Deterministic, with an engine-owned cache, and in the vectors. The hash is SHA-256 over canonical markdown (CommonMark, NFC, LF, trailing whitespace trimmed). Text and hash come back as artifacts the host keeps as evidence. It drafts a text template too, such as the schedule. Each document drafts its own text and hash.
Formulas
Checked only by running: a formula that throws is a Fault. Grammar variables are checked against the model when the archive loads.
Offsets
Time zones are for rendering only. Drafting writes every date-time in one fixed offset: utcOffset from the agreement's data, else the template's default, else +00:00. A clause takes its parent's offset only through a binding in the parent's slot declaration; nothing is copied implicitly.
Runtime text
Data or drafted. Handlers write no prose: a string a handler writes, such as a decline's reason, is fixed text, and names, amounts and dates go in typed fields beside it. A lint flags strings built from data values. Where the wording matters, such as a formal notice the terms fix, the logic drafts it with self.draft. So a second engine has no formatting to match.
Formatting
Locale formatting that comes from the runtime (Intl, toLocale*) is a known risk, linted first and tracked in template-engine#228.

No. 8 · The Recorder · Effects, notifications and timers

Logic decides. The world can still say no.

The Recorder posts what the agreement decided. What logic emits leaves the engine as data. An effect is an act the agreement depends on, and its outcome comes back as a request. A notification is for observers, and nothing comes back. Deadlines leave the same way, as timers.

Shape
abstract event Emitted { id, revision, ordinal }
abstract event Notification extends Emitted { } // self.notify(n)
abstract event Effect extends Emitted { }       // self.emit(e)
abstract event Obligation extends Notification {
  PartyRef obligor, PartyRef obligee, DateTime dueAt? }
event PaymentObligation extends Obligation {
  PreciseAmount amount, String description? }
transaction EffectOutcome { effectId,
  status: SUCCEEDED | REJECTED, detail }
self.setTimer(id, at, request) · self.cancelTimer(id)
Effects
A payment or a formal notice: anything that always gets an outcome. If the terms give delivery a consequence, such as a notice period counting from receipt, it is an effect.
Notifications
Delivered at least once from a transactional outbox, with no ordering promise; a consumer that needs order sorts by (revision, ordinal).
Outcomes
Sent by the system principal to the instance that emitted the effect, and handled by onOutcome. Can't be declined. Duplicates are discarded against the pending effects.
Pending
Logic marks an effect as pending when it emits it, and as done only when a SUCCEEDED outcome arrives; on REJECTED it takes the effect off again. To enforce a limit, such as a spending cap, a clause adds two amounts: what the system of record already shows, which it reads as a fact, and its own effects still pending. It never asks the system of record to reserve anything.
Obligations
Notifications that a party owes performance, such as PaymentObligation or NoticeObligation. The performance itself arrives later as a request. A PaymentObligation's description is optional, and its strings are fixed text or drafted, like any runtime text.
Timers
For dates the terms name, per instance, computed from data with the calendar functions. A firing carries its due time, so each missed occurrence fires once, in order.
Operator dates
End of day, month-end and cut-offs are requests the host sends as the system principal to each instance whose template lists the operator's interface, such as a month-end interface, in implements. Such a request extends OperatorRequest. A missed one is sent once per occurrence, in order.
Time
ISO 8601 date-times with an optional offset, where none means UTC. No time zones and no time-zone database in the engine. A business date, or any other calendar position the operator owns, is a host fact.

A licence fee the payment provider refuses

  1. The licensor asks for payment. The host attests the licensor's principal and triggers PaymentRequest. The licence moves the fee to DUE, emits a collection effect and marks it pending, notifies a PaymentObligation, and sets a timer for the due date.
  2. The host delivers it. The payment provider refuses: the licensee's card was declined.
  3. The outcome returns. EffectOutcome {REJECTED} arrives at the delivery time and reaches the licence's onOutcome handler. The licence clears the pending collection and leaves the fee DUE. Nothing was ever recorded as paid.
  4. The timer fires. At the due date the licence triggers PaymentOverdue on its late payment clause, which sends the first reminder as a notice effect.

No. 9 · The Moot · Vectors and testing

The record is the specification.

At the Moot, practice sessions are recorded, and the record becomes the specification. Golden test vectors define the interface: inputs to semantic body, byte for byte. They are JSON data, each engine ships a thin runner, and the spec is proven when two independent engines pass the same vectors, both drafting through the reference drafter.

Shape
{ id, semantics, archives, agreement, steps }
step 0  = instantiation (init, revision 0)
step n  = { request, inputs, expect: { result, body } }
archives/<hash>/                           // stored by hash
Canonical form
RFC 8785 JSON. PreciseAmount's form follows template-engine#228.
Facts
A step's inputs hold the host facts, so a replay uses the recorded values. Provided facts are not recorded: a replay computes them again.
Two comparisons
Engine conformance: the same archive gives the same bytes on every engine. Template regression: a predecessor's vectors rerun with the new archive, and every field in the old body must match; a Rejection may not become a commit, or a commit a Rejection.
Faults
Until stable Fault kinds land with template-engine#228, a Fault step expects only "result": "Fault", never a body.
Primitive suites
Canonical JSON, decimals and rounding, drafting, hashing and calendars, each tested on its own as {op, args, expect}. Signature checks belong to the host's trust layer, not the engine.
Reference model
A formal kernel model (Lean) generates and explains the vectors where it applies.
Determinism
In 1.0 template code keeps to it by convention and lint. A sandbox of denied globals, stable Fault kinds and transient resource limits are deferred to template-engine#228.
Test host
APAP, the Accord Project Agreement Protocol and its server, is the test host. It records a template's sessions as vectors, each marked as recorded or written by hand. A recording freezes bugs too, so it is reviewed before it counts. A minor version must pass its predecessor's vectors.

No. 10 · The Porters' Lodge · The host

The engine keeps no keys. The porter keeps them all.

The engine has no clock, no storage, no network and no keys; the porter at the Lodge, the host, keeps them. Loading an agreement, committing its result, delivering what it emits and verifying signatures are the host's business. Accord Project states what a host must supply and do, and APAP is the test host that implements it. Accord Project ships no separate reference host.

The hostRequirement
VerifiesAuthenticates callers and checks signatures against the trust profiles it declares, keeping the raw signatures for the evidence
SuppliesThe principal and its assurances, the business time, the requestId, any expect the caller names, and every fact the agreement's templates read that no ancestor provides, read once per request with its record version and keyed by the reading instance and the read's name
Keeps the snapshot trueHolds the records it read until the commit's effects are taken, or checks their versions before committing and triggers the request again with fresh facts
PersistsStates and revisions, serialising concurrent requests however it likes, and lineage where it needs one
DeliversEffects until each has an outcome, each outcome to the instance that emitted the effect, and notifications at least once from a transactional outbox
RendersDates in the agreement's utcOffset, and what a signer sees from the drafted text, recording the renderer version
SchedulesFires the timers a result sets, and sends operator requests as system requests, one per occurrence
DeduplicatesIdempotent redelivery, and rejections cached by requestId
KeepsAudit logs, artifacts and evidence, and the template versions needed for replay

Template authors change

  • Nothing, to keep an existing template running: a compatibility adapter runs an existing TemplateLogic class as an agreement of one template, exactly as today: on the machine's clock and with no identity. You test it on APAP. To use what 1.0 adds, follow the Checklist.

What you get

  • Any host: serverless, a commercial core, or a mock.
  • Safe retries, because the call is pure, including a retry with fresh facts.

For template authors

The Checklist

To move a template to the 1.0 API, do these in order. None of it is needed to keep a current template running under the adapter.

  1. Import the @1.0.0 base namespaces.
  2. Remove @template and extend TemplateData. If the template has logic, add one StateData subtype, empty if it keeps nothing. A text template, such as a schedule, needs no logic and no state.
  3. Use PreciseAmount for money and PartyRef for parties.
  4. Optionally, move a reusable clause into its own archive and list the interface it implements in its manifest's implements. In the interface namespace, describe each member with @Returns, @Declines and @Emits. Declare the parent's slot in its manifest's slots, and bind any value the clause needs from the parent, such as utcOffset. If a document relies on another, such as a schedule, declare it in documents.
  5. Declare the facts the template reads in reads and read them from self.facts. Keep no copy of what a system of record holds. To share a parent's live state with its clauses, provide it as a fact.
  6. Replace the TemplateLogic class with defineLogic().init().on().onOutcome(). Keep handlers synchronous, and change state only with setState.
  7. Take identity and time from self.principal and self.now, never from the request, and business dates from host facts. Check an approval by its assurance's digest, over the request, the text hash, the approval's id and the terms version, rather than by verifying a signature.
  8. Decline by returning a Declined subtype the member lists, or pass a clause's decline up unchanged; throw only for a real error.
  9. Emit acts the agreement depends on as effects, record them as pending, count them against the facts you read, and handle every outcome. Send what observers need, including obligations, as notifications.
  10. Set timers for the dates the terms name, and list the operator's interfaces in implements for end of day or month-end.
  11. Write no prose in handlers: keep strings fixed, and put names, amounts and dates in typed fields. Draft wording that matters with self.draft.
  12. Make every value with a generated factory.
  13. Record sessions on APAP, review them, and ship them as vectors.

A walk through the Accord Project Agreement 1.0 draft proposal, in ten stops. It is for discussion: nothing here is released, and names and shapes may change before 1.0.

Release criteria: composition counts as proven when a composed agreement's test vectors pass, and 1.0 freezes only after a second, independent engine passes the same vectors byte for byte.

The design builds on models#200 and models#205, the engine in template-engine#187, and cicero-core from template-archive#946 and #950. Determinism work is tracked in template-engine#228.
